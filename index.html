About

Over the past two-plus years I've built up working knowledge of Unity and PyGame as my daily-driver engines, with Panda 3D in the mix more recently for Python-friendly 3D work. I focus on small, complete projects rather than vague proofs-of-concept: pick a single mechanic, build it from scratch, then iterate on feel until it's actually fun to play. The technical skills I've ended up caring about most are the unglamorous ones — keeping the game loop tight, making feedback land within a frame or two of input, designing input that translates cleanly between keyboard, controller, and touch.

A lot of my favorite playtesting happens at home — my two nephews (eight and ten) sit down and tear my prototypes apart in the most useful way possible. If a control scheme isn't obvious in ten seconds the eight-year-old quietly hands the iPad back, and if difficulty doesn't ramp visibly the ten-year-old loses interest. They've made me a much sharper self-editor.

Block Stacker

A two-player block-stacking game. Each player owns a 10×18 grid; clearing more than one row at a time sends a garbage row to the opponent. Built to learn local multiplayer in Unity and cross-platform input — the same script runs on a keyboard on PC and on swipe/tap on iPad.

  • Grid mechanics from scratch — no third-party puzzle library — so collision, locking, and row clearing all stay legible
  • Wall-kick rotation with a fallback ladder (center → ±1 → ±2) for forgiving controls
  • Unified InputAxis abstraction so keyboard arrows and on-screen swipes both produce the same Move/Rotate/HardDrop events
  • Garbage system that's symmetric — both players share the same script with playerIndex and an opponent reference
view code snippet (locking + row clear + opponent garbage) 
void Lock() {
    foreach (var c in _piece.Cells())
        if (c.y < height) _grid[c.x, c.y] = _piece.colorId;

    int cleared = ClearFullRows();
    if (cleared > 1 && opponent != null)
        opponent.ReceiveGarbage(cleared - 1);

    if (!SpawnPiece()) _gameOver = true;
}

public void ReceiveGarbage(int rows) {
    for (int y = height - 1; y >= rows; y--)
        for (int x = 0; x < width; x++) _grid[x, y] = _grid[x, y - rows];
    int gap = Random.Range(0, width);
    for (int y = 0; y < rows; y++)
        for (int x = 0; x < width; x++) _grid[x, y] = (x == gap) ? 0 : 8;
}

Train Runner

An on-rails game where you drive a train down a three-lane track, switching lanes to dodge obstacles and boosting or braking to time your runs. Built specifically to practice the same project shipping cleanly to PC and iPad without two separate input paths.

  • Lane-based movement with smooth lateral interpolation — no snapping, no overshoot
  • Speed system with brake and boost, ramped via Mathf.MoveTowards so input feels weighty rather than instant
  • Single input path handles WASD/arrows on desktop and swipe gestures on iPad (horizontal swipe → lane change, vertical → boost/brake)
  • Physics.CheckSphere against a dedicated obstacle layer for collision — small enough to read top to bottom

if (Input.touchCount > 0) {
    var t = Input.GetTouch(0);
    if (t.phase == TouchPhase.Began) { _touchStart = t.position; _tracking = true; }
    else if (_tracking) {
        Vector2 delta = t.position - _touchStart;
        if (Mathf.Abs(delta.x) > swipeThreshold && Mathf.Abs(delta.x) > Mathf.Abs(delta.y))
            laneDelta = delta.x > 0 ? +1 : -1;
        else if (Mathf.Abs(delta.y) > swipeThreshold)
            speedTarget = delta.y > 0 ? baseForwardSpeed * boostMultiplier
                                       : baseForwardSpeed * brakeMultiplier;
    }
}

Orbital Dodge

A one-screen arcade game where you orbit a planet and dodge inbound asteroids. Originally a Saturday-afternoon build for my eight-year-old nephew, who promptly demanded a high-score counter and "more asteroids that wiggle." Both got added in v2.

  • Player position is stored in polar coordinates so radial input maps cleanly to "push out / pull in"
  • Angular speed scales inversely with orbit radius — closer to the planet feels frantic, far out feels stately
  • Deterministic spawner with a difficulty curve that tightens spawn interval over elapsed time
  • Slot-based Asteroid class to keep allocations down and inspect-able state minimal
view code snippet (polar movement + spawner) 
class Player:
    def update(self, dt, keys):
        # angular speed feels more natural when it scales with radius
        ang = PLAYER_ANGULAR_SPEED * (180.0 / max(self.orbit, 1.0))
        if keys[pygame.K_LEFT]:  self.theta -= ang * dt
        if keys[pygame.K_RIGHT]: self.theta += ang * dt
        if keys[pygame.K_UP]:    self.orbit += PLAYER_RADIAL_SPEED * dt
        if keys[pygame.K_DOWN]:  self.orbit -= PLAYER_RADIAL_SPEED * dt
        self.orbit = max(PLAYER_MIN_ORBIT, min(PLAYER_MAX_ORBIT, self.orbit))

# spawn interval decays over elapsed time → mild difficulty curve

First-Person Explorer Controller

A compact movement controller for a kid-friendly Minecraft-style exploration game I'm building so my nephews can walk around a little world and find hidden chests. The constraint was "stay under ~120 lines so every system stays legible" — it's also the script I keep copy-pasting into new prototypes whenever I need first-person movement.

  • CharacterController-based movement with separate tracking of horizontal and vertical velocity
  • Mouse-look with pitch clamping; cursor locked on start
  • Jump height computed from kinematics: v = sqrt(2 · g · h)
  • Sinusoidal head-bob whose frequency scales with current ground speed; eases back to rest when stopped

void HandleMove() {
    Vector2 input = new Vector2(Input.GetAxisRaw("Horizontal"), Input.GetAxisRaw("Vertical"));
    if (input.sqrMagnitude > 1f) input.Normalize();
    float targetSpeed = Input.GetKey(KeyCode.LeftShift) ? sprintSpeed : walkSpeed;
    Vector3 worldTarget = transform.TransformDirection(new Vector3(input.x, 0f, input.y) * targetSpeed);
    _horizontalVel = Vector2.MoveTowards(_horizontalVel, new Vector2(worldTarget.x, worldTarget.z), acceleration * Time.deltaTime);

    if (_cc.isGrounded) {
        if (_velocity.y < 0f) _velocity.y = -2f;
        if (Input.GetButtonDown("Jump"))
            _velocity.y = Mathf.Sqrt(jumpHeight * -2f * gravity);
    }
    _velocity.y += gravity * Time.deltaTime;
    _cc.Move(new Vector3(_horizontalVel.x, _velocity.y, _horizontalVel.y) * Time.deltaTime);
}

What I've learned from my playtesters

Building games for two specific kids — instead of "a player" in the abstract — has changed how I design. The eight-year-old taught me that controls have to be discoverable without instructions; if a button isn't obvious, he just won't press it. The ten-year-old taught me that difficulty has to ramp visibly, or he'll declare the game "boring" and walk away. Between them they've turned me into a much harsher self-editor: every screen has to earn its keep.

The skills that have actually compounded are the unglamorous ones — keeping the game loop tight, making feedback land within a frame or two of input, and resisting the urge to add features before the core mechanic is fun on its own.
